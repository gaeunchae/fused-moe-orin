# Bytes per Block: Fast Batch-1 MoE Decoding on Jetson AGX Orin

Course project for Computing for Data Science 2 (Fall 2026).

## Summary

On a Jetson AGX Orin, llama.cpp decodes Qwen3-30B-A3B (Q4_K_M) at 43.4 tokens/s. That is 46% of the 94 tokens/s its measured 180 GB/s bandwidth allows.

Profiling with the transfer cost subtracted points at the single-token quantized GEMV kernels. They read exactly their weight bytes, but at about half the bandwidth.

- **Cause:** fine-grained experts have short rows (432 B for a Q4_K row of 768 weights). With one row per thread block, Orin's 16 SMs cannot keep enough bytes in flight.
- **Fix:** we replace llama.cpp's per-format block shapes with a rule computed from bytes per block and registers per thread, and add two dedicated MoE kernels.

Decode speed on Orin, tokens/s at context 0:

| Model | llama.cpp 13ec8f6 | llama.cpp master e300919 | Ours (patch on e300919) | vs master |
|---|---:|---:|---:|---:|
| Qwen3-30B-A3B | 43.4 | 48.3 | 61.6 | +28% |
| Qwen3.5-35B-A3B | 39.6 | 45.8 | 53.7 | +17% |
| OLMoE-1B-7B | 115.2 | 129.2 | 163.1 | +26% |

- **Correctness:** all 5,411 MUL_MAT, MUL_MAT_ID and MUL_MAT_FUSION tests in `test-backend-ops` pass, and perplexity is unchanged within error.
- **Second GPU:** on an RTX 3090 the kernel-level effect reappears, but the end-to-end gain is 2 to 3%.

## Build and run

You need a Jetson AGX Orin (sm_87) or another NVIDIA GPU (use its architecture, for example 86 for an RTX 3090), CUDA 12.4 or later, and CMake. Run these from the repository root:

```
git clone https://github.com/ggml-org/llama.cpp && cd llama.cpp && git checkout e300919
F="-DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=87 -DCMAKE_BUILD_TYPE=Release"
F="$F -DLLAMA_BUILD_TESTS=ON -DCMAKE_CUDA_COMPILER=/usr/local/cuda/bin/nvcc"
# baseline first; do not rebuild build_base after the patch is applied
cmake -S . -B build_base $F && cmake --build build_base -j 8 --target llama-bench
git apply ../patches/bytes_rule_master_e300919.patch
cmake -S . -B build_ours $F
cmake --build build_ours -j 8 --target llama-bench test-backend-ops

# decode speed: baseline, then ours (the dedicated kernels are on unless set to 0)
M=Qwen3-30B-A3B-Q4_K_M.gguf
build_base/bin/llama-bench -m $M -ngl 99 -p 0 -n 64 -d 0,1024,4096 -r 5
export GGML_CUDA_MMVQ_BYTES=8192
build_ours/bin/llama-bench -m $M -ngl 99 -p 0 -n 64 -d 0,1024,4096 -r 5

# correctness (repeat with -o MUL_MAT and -o MUL_MAT_FUSION)
build_ours/bin/test-backend-ops test -b CUDA0 -o MUL_MAT_ID
```

**Models.** Download the Hugging Face checkpoints (Qwen3-30B-A3B, Qwen3.5-35B-A3B, OLMoE-1B-7B-0125-Instruct). Convert them with llama.cpp's `convert_hf_to_gguf.py`, then quantize with `llama-quantize <in.gguf> <out.gguf> Q4_K_M`.

**Runtime switches** (all read once per process):

| Variable | Effect |
|---|---|
| `GGML_CUDA_MMVQ_BYTES=8192` | Enables the block-shape rule with an 8 KB target per block. Unset, the stock tables apply. |
| `GGML_CUDA_MMVQ_SHAPE=w,r` | Forces one shape (w warps in {1,2,4}, r rows in {1,2,4,8}). For experiments. |
| `GGML_CUDA_MOE_GLU=0`, `GGML_CUDA_MOE_DOWN=0` | Turn off the dedicated gate+up and down kernels (on by default). |
| `GGML_CUDA_MOE_PREFETCH=n` | L2 prefetch distance of the gate+up kernel, in blocks (default 64). |

## Benchmarks (`bench/`)

**Main benchmarks used in the report**

- `gemv_shape.cu`: standalone CUDA. It follows llama.cpp's `mul_mat_vec_q` dot product and reduction, on real Q4_K weights.
    - Section D cuts one expert matrix into rows of 512 to 4096 weights at equal total bytes and times 75 block shapes (Figures 1 and 2).
    - A fourth argument restricts the kernel to that many SMs with a CUDA green context (Figure 3).
    - `data/tensor_index.tsv` holds offsets for our GGUF file. For your own file, regenerate it with `python3 -I scripts/gguf_index.py MODEL.gguf data/tensor_index.tsv`.
    ```
    nvcc -O3 -std=c++17 -arch=sm_87 -o gemv_shape bench/gemv_shape.cu -lcuda
    ./gemv_shape MODEL.gguf data/tensor_index.tsv D        # row-length sweep
    ./gemv_shape MODEL.gguf data/tensor_index.tsv D 8      # same on 8 SMs
    ```
- `mmid_formats.cpp`: times llama.cpp's own single-token MUL_MAT_ID through the ggml CUDA backend.
    - It covers 13 formats and 5 row lengths, plain (down-like) or fused gate+up.
    - Link it against a build's ggml libraries to compare builds:
    ```
    g++ -O2 -std=c++17 -Illama.cpp/ggml/include bench/mmid_formats.cpp \
        -Lllama.cpp/build_ours/bin -lggml -lggml-base -lggml-cuda \
        -Wl,-rpath,$PWD/llama.cpp/build_ours/bin -o mmid_formats_ours
    ./mmid_formats_ours all fused          # [TYPE|all] [plain|fused] [COLS]
    ```
- `dense_shapes.cpp`: the same for dense single-token MUL_MAT over matrix sizes.

**Exploratory probes** from the profiling stage:
- `orin_bench.cu`: bandwidth versus bytes per launch, and launch cost.
- `gemv_decomp.cu`, `gemv_down.cu`, `gemv_layout.cu`, `gemv_prefetch.cu`: cost decomposition and kernel variants.
- `sparse_locality.cu`, `moe_probe.cpp`: activation-sparsity study.
- `addr_probe.cpp`: expert weight addresses.

## Scripts (`scripts/`)

The shell drivers set the paths to builds, models and outputs at their top. Edit those for your machine.

| Script | Purpose |
|---|---|
| `validate_master.sh` | Tests, format benchmark and decode speed against llama.cpp master, in one run (about 40 minutes on Orin). |
| `shape_sweep.sh`, `shape_analysis.py` | Every forced block shape × plain/fused × 65 configurations, and how close each rule comes to the best shape. |
| `accuracy.sh`, `compare_logits.py` | Teacher-forced logit agreement and single-token perplexity. |
| `profile_breakdown.py`, `floor_breakdown.py`, `nsys_depth_sweep.sh` | Per-token time split into the transfer floor and the time above it, from node-level nsys traces. |
| `kernel_summary.py`, `ncu_token.sh`, `ncu_summary.py`, `host_gap.py` | Kernel, Nsight Compute and host-side summaries. |
| `make_figures.py`, `report_pdf.py` | Figures and the report PDF. |
| Others | Experiments recorded in `RESULTS.md`, including the RTX 3090 analysis. |
